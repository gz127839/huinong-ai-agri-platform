四、从"实验室准确"到"田间可用"（本项目最关键的一步）

标准数据集是实验室条件下拍的：叶片居中、光照均匀、对焦清晰。但用户真正使用手机在田里拍出来的照片， 往往角度歪、主体偏移、光线忽明忽暗、还可能失焦。为此我额外构造了 {{ bench.dataset.perturbed }} 张田间扰动测试图 （随机旋转 ±28°、主体缩放至 72%~95%、亮度 0.68~1.32、对比度抖动、40% 概率高斯失焦、随机 JPEG 压缩）， 专门用来检验模型在真实拍摄条件下的表现。

七、开放集识别：让模型"知道自己不知道"

分类模型只能在已知的 38 个类别里挑答案，遇到训练集外的作物（小麦、水稻等）会强行给出一个最像的结论—— 我用一张真实用户上传的水稻稻穗照片实测：旧版闭集分类器以 100.0% 置信度判成"葡萄蔓枯病"并输出了完整用药建议， 这在农业场景有误导用药的真实风险。 解决方案：为每个类别建立特征中心，推理时计算图片特征与最近中心的余弦相似度， 低于阈值即主动拒识，如实告知支持范围，而不是编一个答案。

为什么光有"相似度阈值"还不够：物种通道的可拒识改造

上面这套阈值是在已收录作物上调出来的，对"库里根本没有的作物"几乎不设防。 我实测了 {{ species.eval.neg_species | length }} 种平台未收录作物、共 {{ species.eval.neg_n }} 张田间实景照： 改造前有 91.2% 被强行判成库里某个作物 （白菜→油菜 100%、桃→苹果 96.7%、甘蔗→玉米 96.7%）—— 这正是"喂什么图都给你配一个答案"的根源。 改造办法不是继续调阈值，而是让模型自己学会说"不认识"： ① 把未收录作物的实景照作为第 15 类「未收录/其他」参与训练； ② 1-NN 最近邻距离兜底，挡住训练集完全没见过的东西； ③ 为物种通道单独微调骨干网络（MobileNetV2），让特征本身更能区分作物。

九、能力边界：模型会什么、不会什么（如实说明）

做农业 AI 最怕"什么图都敢给结论"。本平台把能力边界写清楚，并在产品层面做了双通道 + 三层分流：

能做的
① 叶片病害诊断：14 种作物的叶片病害图像诊断（{{ ai_model_crops }}）， 标准测试集作物 99.0% / 病害 97.1%，田间扰动图 86.3% / 94.6%。
② 作物物种识别（实景照）：在 2 511 张 iNaturalist/GBIF 研究级田间实景照片上训练的 物种分类通道（骨干为作物数据微调过的 MobileNetV2），覆盖知识库全部 14 种作物 （含叶片模型没学过的{{ kb_only | join("、") }}），田间实景留出集准确率 {% if species.eval %}{{ species.eval.in_scope_test_acc }}%{% else %}约 89%{% endif %}， 并且对未收录作物会主动拒识而不是强行配对。
做不到的
病害诊断模型只在 5 万张叶片样本上训练，果实、籽粒、整株照片只能识别"是什么作物"， 给不出病害结论；物种通道对光照/背景复杂的个别种类（茶树、大豆）仍会认错， 所以所有实景识别结果都标注"仅供参考"，并给出置信度与匹配度。
四层分流
① 叶片且在范围内 → 出病害结论 + 置信度 + 热力图；
② 实景照/果实照 → 物种识别通道回答"这是什么作物"（置信度 + 原型匹配度双重门控）， 并引导上传叶片做病害诊断；
③ 物种通道也没把握 → 通用视觉模型（ImageNet）认外观品类；
④ 仍超出范围 → 开放集拒识，同时直接给出该作物的知识库科普与防治资料，不让用户空手而归。

这样做的原因：宁可如实说"不会"，也不能让农户拿着错误的病害结论去打药。 物种通道的训练数据来自 GBIF/iNaturalist 开放数据，按同样方法即可继续扩充新的作物种类。

十、农业智能体：从"能问答"到"能办事"

识别模型与知识库解决的是"看得准、查得到"，但要真正帮农户解决问题，还需要一个能 自己规划步骤、调用工具、看结果再决定下一步的智能体。

目标 → 规划 → 调工具 → 观察结果 → 再规划 → … → 汇总成可执行方案

关键差别在于那条从"观察"回到"规划"的反馈回路——普通问答只有一次生成， 智能体会根据工具真实返回的数据不断调整下一步动作。

工具箱
recognize_image 图像识别（三通道）、crop_profile 作物档案、 query_disease 病害防治方案、search_knowledge 知识库检索、 list_products 农资价格库存——全部复用平台已有能力，不是另起炉灶。
典型链路
用户上传照片并说"叶子发黄怎么办" → 智能体先调识别（认出水稻 66.6%） → 据识别结果查水稻档案 → 再查水稻病害防治 → 输出症状、用药、田间整改与采购建议。 每一步的工具名、参数、返回与耗时都在页面上如实展示。
规划器
默认走云服务免密钥大模型（无需申请任何 API Key，开箱可用）； 也可在环境变量里换成自备的 OpenAI 兼容接口。两者都不可用时由 内置规则规划器接管，按语义与识别结果自动编排工具顺序， 链路完全一致，断网环境也能完整演示。

十一、大模型集成：选型、Prompt 设计与可控性

平台在两个场景真正用上了大模型：农技问答（RAG 检索增强生成）与 农业智能体（工具自主规划）。模型层统一收敛到 llm_client.py 一个模块，双通道热切换，业务代码零改动。

模型选型
默认接入腾讯混元 hunyuan-chat（云服务免密钥通道，开箱可用、无需申请 Key）； 主模型异常时按序兜底 glm-5.3-flash → deepseek-v4-flash， 单次调用失败自动换模型，不把错误抛给用户。也支持一键换成自备的 DeepSeek / 通义 / 智谱等任意 OpenAI 兼容接口（3 个环境变量）。
Prompt 设计
① 问答：强制"仅依据【参考资料】回答，没有就建议咨询农技站"，逐条编号拼装检索上下文； ② 智能体：ReAct 协议（思考 → 行动(JSON 参数) → 观察 → finish）， 规定"至少 2 次有效工具调用前不允许 finish"、禁止无图调用识别工具、 病害/药剂/剂量必须来自工具返回；③ 输出统一约束为面向农户的简体中文分条纯文本。
输出稳定性
温度压低（问答 0.3 / 智能体 0.2）+ max_tokens 上限 + SSE 流式拼装 + 后处理清洗 Markdown 符号；接口超时、空返回、参数不兼容均有兜底链， 断网时问答降级为知识库原文、智能体降级为规则规划器，功能永不中断。
安全与可控
答案锚定检索/工具返回数据抑制幻觉；用药建议强制附带安全间隔期与 "先小面积试用"提醒；每页输出结尾带"仅供参考，结合田间实际复核"免责声明； 拒答边界明确——知识库未收录就如实说明，不编造。
工具集成
智能体工具采用「名称 + JSON Schema 参数 + 结构化返回」的统一抽象， 5 个工具全部复用平台真实数据，新增工具只需注册一个 dict，模型侧提示词自动更新； 同一批工具同时以标准 MCP 服务端对外开放（见下一节）， 站内智能体与外部 AI 客户端看到的是完全一致的能力。

十二、MCP 工具服务：把农业能力开放给任意 AI 客户端

平台不只是「用」大模型，还把自身的农业能力按 Model Context Protocol（MCP） 标准对外开放。服务端 mcp_server.py 用标准库手写 JSON-RPC 2.0 与 stdio 传输， 零第三方依赖，任何支持 MCP 的客户端（Claude Desktop、WorkBuddy、Cline、自研 Agent） 配置后即可直接调用，无需改一行代码。

协议实现
完整实现 initialize（版本协商 2025-06-18 / 2025-03-26 / 2024-11-05）、 tools/list、tools/call、ping 与 notifications/initialized；stdout 只走协议帧、日志统一写 stderr， 参数缺失与工具异常以 isError 结构化返回，不会打断会话。
对外工具（5 个）
recognize_image 图像识别（叶片病害 → 实景物种 → ImageNet 三通道级联，超范围主动拒识）、 crop_profile 作物档案、 query_disease 病害防治方案、 search_knowledge 知识库检索（RAG 召回）、 list_products 农资与农产品价格库存。
同源实现
MCP 服务端与站内智能体调用的是同一份 agri_agent.TOOLS 函数表， 数据全部来自平台 SQLite 知识库与本地 ONNX 模型， 因此外部客户端拿到的结论与网页端逐字一致，不存在两套逻辑。
可复现验证
python mcp_server.py --selftest 一条命令跑通握手、工具枚举、真实调用； --tools 打印工具清单；项目根目录 mcp.json 给出客户端配置模板。
