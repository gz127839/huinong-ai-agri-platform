# 慧农 AI · 智慧农业助农服务平台

> 电脑和手机都能用的智慧农业平台，核心是一套真正跑得起来的作物病害识别模型。
> 技术栈：Flask + SQLite + ONNX Runtime（MobileNetV2）+ 原生响应式前端

---

## 一、为什么做这个平台

我国种地的主体还是分散经营的小农户。跟他们聊下来会发现，难处往往不在肯不肯下力气，而在几个具体的信息缺口上。

最常见的是认不出来。叶子起了斑，凭经验拿不准是什么病，等农技员下乡，最佳处置期已经过去了。就算认出来了，还有第二道坎：知道是病，但不知道该打什么药、什么时候打、打完田间怎么管。最后是卖的问题，农产品缺少展示渠道，中间环节一层层加价，好货卖不出好价。

这三件事本来各有各的解决方式，但农户手里只有一部手机。所以我们把它们放进同一个平台：拍照认作物，辨认病害，拿到能照着做的防治方案，产出达标农产品后直接上架展销，采购方可以直接来问。从认到卖，一次登录走完。

## 二、和政策方向的对应

平台定位是助农服务，服务对象明确指向普通农户，这与乡村振兴、农业农村优先发展的方向是一致的。识别、诊断、科普、展销全流程在线完成，降低的是信息获取的门槛，对应数字乡村建设。首页首屏做了一条政策宣传条，滚动展示这些内容。

"藏粮于地、藏粮于技"里的"技"，在这个平台上就是作物科普和病虫害防治知识库，不用等培训，打开就能查。用深度学习替代凭经验判断，是农业新质生产力在基层的一种具体落法。知识库覆盖玉米、马铃薯、大豆等主要粮食作物，粮食安全这条线也就守住了。

## 三、四个功能模块

### 1. 农作物识别与科普（`/crop-recognize`）

电脑上直接上传图片，手机上点"拍照识别"会调起后置摄像头。模型给出作物类别和置信度，同时列出 Top-3 候选，避免只给一个答案让人无从判断。

识别之后接的是科普内容：这种作物适合种在什么地区、什么季节，生长习性如何，田间怎么管，经济价值在哪里。对不认识的作物或者果实特写，系统不会硬猜，会说明超出范围，并给出引导。果实照片则由通用视觉模型兜底，先告诉你这是什么，再提示补拍叶片做病害诊断。

### 2. 病虫害诊断与防治（`/disease-recognize`）

模型分三层做判断：先定作物，再在该作物的病害范围内细分到 38 个类别，同时给出健康概率。健康判定是单独一条：叶片上确实没有明显病斑时，页面会明确说"未见明显病斑"并给预防建议，而不是随便开一套药。

诊断结果附带四套防治方案，物理防治、合理用药（含药剂、时机、安全间隔期）、田间整改、后期预防，都能直接拿去用。结果页还有一张遮挡敏感度热力图，标出模型判断时真正关注的叶片区域，看得见依据，不是黑箱。

真遇到没学过的作物，页面不给病害结论，但仍然把该作物的知识库资料摆出来，不让用户空手而归。

### 3. 农产品助农展销（`/shop`）

这个模块定位在展示与咨询，不接支付，更贴近助农撮合的实际情况。功能上包括商品展示、分类筛选、搜索排序、采购清单、需求单、农户上架（需后台审核）和咨询留言。

后台 `/admin` 可以审核商品、处理需求单、回复留言、查看识别记录。

### 4. AI 能力实验室（`/ai-lab`）

模型结构、训练方法、评测指标、开放集拒识的真实案例（含修复前后对比）、能力边界，都放在这一页。评测数据、失败案例、边界条件全部公开，模型做到了什么、没做到什么，翻一遍就清楚。

## 四、AI 技术方案

### 4.1 为什么选 MobileNetV2

先说没选的路。把识别交给云端大模型 API，农村网络不一定稳，按次收费，断网就废，识别必须能离线跑。换更大的视觉模型（ViT 一类），准确率或许还能高一点，但普通电脑 CPU 推理慢，部署门槛直接劝退。手写特征规则（比如 HSV 颜色比例）看起来能用，实际上不是从数据里学出来的东西，准确率低也没法泛化，只保留作模型缺失时的应急通道。

最后选的是 MobileNetV2 迁移学习，导出 ONNX 在 CPU 上推理。ImageNet 的预训练权重迁到农业领域，14MB 模型，毫秒级推理，全程离线，村级电脑也跑得动。

语言组织这部分交给云端大模型，但它只负责把检索到的资料说通顺，识别和结论始终来自本地模型。断网时自动降级为知识库检索或规则规划器，功能不中断。

### 4.2 模型与训练

数据用的是 PlantVillage 公开数据集，54,305 张带标签的叶片图，覆盖 14 种作物、38 个病害与健康细类。按 8:1:1 分层划分训练、验证、测试，随机种子固定为 20261024，结果可复现。

训练时冻结 MobileNetV2 主干，提取 1280 维嵌入，在上面训练三个分类头：作物 14 类、病害细类 38 类、健康二分类。权重导出成纯 NumPy 文件，配合 ONNX Runtime 做 CPU 推理。

针对手机实拍的抖动、暗光、模糊，训练阶段专门做了退化增强：旋转 ±28°、主体缩放 0.72~0.95、亮度 0.68~1.32、高斯失焦、JPEG 压缩。样本少的病害类做平衡采样，防止模型整体偏向常见类。推理时对原图和四角、中心裁剪共五个视角取平均，用一点计算代价换稳定性。

### 4.3 开放集识别（AI 部分最关键的改动）

农户拿起手机，什么都会拍。闭集模型遇到没学过的作物时，会强行判成最像的已知类，我们实测过一张小麦照片被判成马铃薯，置信度 99.9%。农业场景里，这种错误会直接变成错误用药。

做法是给 38 个类别各建一个特征中心：取该类训练样本在嵌入空间的均值，做 L2 归一化。推理时计算图像嵌入与最近类中心的余弦相似度，低于阈值 0.75 就判定为范围外，主动拒识。拒识时不编结论，页面说明原因，再把该作物的知识库资料给出来。

阈值是在验证集分布上标定的，已知类误拒率 28/10,858，约 0.26%。这个数看着不高，但它决定了模型敢不敢说"我不知道"。

### 4.4 作物物种识别通道

叶片模型只认识实验室里的叶片。用户传上来的多是田间照、果实照、整株照，这些会被开放集拒识掉，结果就是"知道它不像叶片，但也说不出它是什么"。为此单独加了一条物种识别通道。

数据来自 GBIF 和 iNaturalist 的研究级鉴定照片，2,511 张、14 类，覆盖知识库全部作物，其中水稻、小麦、黄瓜、茶树、油菜是叶片模型完全没学过的。它和病害模型共享同一个 MobileNetV2 骨干，5 视角均值嵌入后接多元逻辑回归，训练用纯 NumPy 实现，没有引入新依赖。田间实景测试集准确率 69.2%，这个数字不高，但比"认不出来"强得多。

门控是双重的：类原型余弦相似度不低于 0.58，且置信度不低于 0.60，才作为正式答案。达不到就标"疑似，仅供参考"，或者转知识库。用 14 张真实白底产品图实测，优化前叶片模型 0/14（全部拒识），物种通道能做到 10/14。

### 4.5 通用视觉兜底

物种通道也没把握的时候，调用 ImageNet 原版 MobileNetV2 再认一次品类。黄瓜 99.9%、苹果 86%，覆盖 22 类常见果蔬。识别出是什么果实之后，提示用户"病害诊断请上传叶片"。两个通道都判不了，就引导到知识库和问答助手。

三个模型各管一段：病害模型管叶片，物种通道管"这是什么作物"，通用模型管果实品类，互相兜底。

### 4.6 农业智能体

问答助手是单向的，检索一次、生成一次。智能体多了反馈回路：规划、调工具、看结果、再规划，直到能给出可执行的方案。

工具箱有五个：`recognize_image` 图像识别（复用上面三条通道）、`crop_profile` 作物档案、`query_disease` 病害防治方案、`search_knowledge` 知识库检索、`list_products` 农资价格与库存。

一个典型链路是这样：用户上传一张稻穗照片问"叶子发黄怎么办"，智能体先识别出水稻（置信度 66.6%），接着查水稻档案，再查水稻病害防治，最后给出症状、用药、田间整改和采购建议。每步调了什么工具、传了什么参数、返回了什么、花了多久，`/agent` 页面上都留着痕。

默认由大模型按 ReAct 协议自主规划，走免密钥云通道，不需要申请 Key。大模型不可用时切到内置规则规划器，同样是走一步看一步，链路一致，断网也能把演示走完。涉及病害和用药的问题强制至少两次工具调用，药剂剂量必须来自知识库，不允许模型自己编。会话内保留最近 3 轮，可以追问。另外开放了 `/api/agent` 的 JSON 接口，方便外部系统调用。

### 4.7 评测结果

| 测试集 | 作物识别 | 病害识别 | 健康判定 |
| --- | --- | --- | --- |
| 标准测试图（10,858 张） | 99.0% | 97.1% | 98.5% |
| 田间扰动图（3,000 张） | 86.3% | 94.6% | 97.8% |

标准集上已经接近饱和，看不出模型在真实场景里的表现。所以又构造了一套模拟田间拍摄的扰动测试集，加入退化增强训练前后，病害识别从 81.3% 提到 94.6%，涨了 13.4 个百分点。

## 五、系统架构

```
浏览器（响应式：PC / 平板 / 手机）
        │
Flask 应用层（app.py：路由 / 会话 / 业务逻辑）
        │
   ┌────┴─────────┬──────────────┐
AI 识别引擎     LLM 问答(可选)   数据层
ai_engine.py   ai_assistant.py  db.py + SQLite
  ├ 特征提取      └ RAG 检索       8 张表
  ├ 三层分类头        + 知识库      自动建库
  ├ 开放集检测        + LLM 生成
  ├ 物种识别通道
  ├ ImageNet 兜底
  └ 热力图 / TTA
```

数据库 8 张表：users、crops、diseases、products、cart_items、orders、messages、history，首次启动自动建库。

登录墙用 `before_request` 统一拦截，未登录访问任何页面都会被带回登录页，`/api/*` 返回 401。登录后按 `next` 参数跳回原本要访问的页面，只认站内相对路径，避免开放重定向。识别记录、采购清单、上架商品都和账号绑定。

前端是 Jinja2 模板加原生 CSS/JS，1080、900、640px 三档断点，手机端可以直接调后置摄像头。

降级链路是层层退守：真模型、通用视觉兜底、知识库资料、本地特征引擎，任何一环失效，服务不会中断。

## 六、创新点

技术上最实质的一条，是把人脸识别领域的开放集检测思路用到了作物病害识别上。农户拍来的东西本来就不在训练分布里，闭集模型硬判才是常态，而农业场景里判错的代价是打错药。加上拒识机制之后，模型至少知道自己不知道。

第二个是分层决策。叶片病害模型当专家，ImageNet 通用模型当通才，中间再加一条物种通道，各管一段、互相兜底。物种通道用的是 GBIF/iNaturalist 的公开数据自建的 14 类实景集，和病害模型共享骨干，不增加推理开销，把"这是什么作物"的覆盖从 9/14 补到 14/14。

训练策略上也有收获。没有换模型、没有加参数，只做了面向实拍的退化增强，扰动集指标就涨了 13.4 个百分点。这说明在农业场景里，数据质量比模型规模更要紧。

工程上坚持用纯 NumPy 权重加 ONNX CPU 推理。14MB 的模型，不需要 GPU，不需要联网，村级电脑能跑，这是它能在农村用起来的前提。

产品层面，智能体不是"接个大模型聊天"就完事。平台的全部能力都被包成标准工具，AI 自己规划先看图、再查档案、再查防治、最后给采购建议，每一步都可见可查，核对执行轨迹就知道是不是真在调工具。

还有一条算是设计原则：宁可说不会。拒识时不给结论，转而给知识库资料。给错结论的代价是农户打错药，如实拒识比虚假的自信有用。

## 七、谁能用上

对普通农户来说，识别和防治的门槛降下来了，误判造成的减产和用药浪费都会少一些。基层农技推广可以把知识库和四套防治方案当培训素材用。合作社和村集体则多了一个零成本的展示渠道，能直接撮合采购。

商业上想的是村级服务站或农资店的 SaaS 订阅，离线部署是卖点。用得越多，积累的实拍数据越多，可以反哺模型扩充水稻、小麦等类目。再往后是和县域农技推广部门共建。模型全程离线，没有 API 成本，单点部署成本很低，这个成本结构适合在农村下沉市场铺开。
